# Guided director demo acceptance

The user enters Hack Harbor five days before doors open, with 180 attendees and
an existing financial situation. This is a fictional practice event in an isolated
run. Subsequent inference, source-version changes, director decisions and report
records use the real application.

## Intended walkthrough

1. **Catch the change.** Compare the original USD 480 AV invoice with the revised
   USD 420 invoice. Ask Finney to reconcile the existing commitment. The result
   must retain one liability and both documents; a second payable is a failure.
2. **Make a decision.** Ask for an AV budget change from USD 800 to USD 1,000.
   Inspect the actual pending proposal and reject it. Ask what that changes. The
   budget stays USD 800 and the supported liability remains owed. No payment or
   approval is invented.
3. **Get the current picture.** Review Mira's personal-card receipt and duplicate
   copy. The supplier is paid; the organizer's supported reimbursement remains
   outstanding. Produce a report that separates cash, commitments and the unpaid
   sponsor pledge. Optional learning inspection shows actual stored experiments.

The user can skip, resume, inspect documents or type a different request. A
walkthrough step is navigation state, not proof that an action succeeded. Pending
jobs, failures and actual recorded outcomes must remain distinguishable.

## Hyphenate criteria and observable proof

| Criterion | What the judge can do or inspect |
| --- | --- |
| Realistic problem, messy data, proof | Read conflicting invoice versions and duplicate receipt; inspect resulting records and source references |
| Useful finance roles with bounded authority | Let the agent investigate/propose; make the director decision; verify it cannot invent permission or settlement |
| Distinctive company/problem/approach | A finance teammate for volunteer hackathon organizers combining ongoing intake, event cash planning and measured procedure learning |
| Memorable catch, recovery and defense | Change a document, reject a proposal, ask why the debt remains, and inspect the resulting explanation and audit trail |

The [sponsor brief](https://docs.google.com/document/d/1u4iN8R97ILY3kfHTPKC82zdutHrGx4ze5eCAP-J92w4/edit)
permits simulations. Synthetic inputs do not establish customer accuracy, savings,
bank settlement or a learned promotion. Those require their own evidence.

## Interface acceptance

- The landing-page demo entry creates or resumes the prepared event after sign-in.
- The first screen establishes the situation and one next action; it is not a tour
  of navigation labels or a collection of unexplained database rows.
- Source documents show their actual contents, including nested evidence bundles.
  Technical identifiers and provenance remain inspectable without dominating.
- Financial amounts and all substantive explanation text survive formatting intact.
- Case-bound upload and conversation keep their context without repeated selectors.
- Desktop and mobile remain readable, operable by keyboard, and free of horizontal
  layout overflow; reduced-motion preferences are respected.
- Actual API outcomes drive preparation, waiting, rejection and recovery states.
